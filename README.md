# rc_longxinnan — 可靠事件通知投递服务

业务系统在关键事件发生时，需要把通知送达外部供应商（广告系统、CRM、库存系统…）。本服务统一收口这些请求：**业务系统只负责"发生了什么"，我们负责"可靠、按各供应商格式送到"**，并对外隐藏供应商差异。

---

## 一、对问题的理解

### 1.1 问题本质

企业内部多个业务系统在**关键事件**发生时，需要调用外部供应商的 HTTP(S) API 做通知。这本质上是**两个耦合问题叠加**：

1. **格式差异**：不同供应商的请求地址、Header、Body 格式各不相同。业务系统若直接对接，就得为每个供应商写一遍适配代码，任何供应商接口改动都会牵动所有业务系统。
2. **可靠性要求**：通知一旦发出就承担了业务后果（用户权益、库存准确性、广告归因）。业务系统本身**不关心外部 API 的返回值**，但要求**通知一定得送达**。

因此需要一个**通知中心**：对外统一收口、屏蔽差异；对内专注做"送达"这件最麻烦的事。

### 1.2 三个典型场景与流量特征

| 场景 | 触发事件 | 目标系统 | 流量特征 | 实时性 | 可靠性 |
|---|---|---|---|---|---|
| 广告引流注册 | 用户经广告成功注册 | 广告系统 | **高量、突发**（用户浏览产生） | 低（延迟几十秒可接受） | 中 |
| 订阅付款成功 | 付款完成 | CRM（改 Contact 状态） | 低量 | **高**（关系到用户权益） | **必须送达** |
| 商品购买 | 下单成功 | 库存系统 | **可能突发** | **高** | **必须送达** |

这三个场景对投递系统提出了**两个相反的诉求**：

- **抗突发流量**：广告引流量大且有尖峰，投递速度不必紧跟产生速度；
- **关键消息绝不丢**：订阅/购买类消息一旦丢了就会损害用户权益。

单一策略无法同时满足——这正是架构的核心难点。

### 1.3 由此推导的核心诉求

1. **屏蔽差异**：供应商差异全部配置化，业务系统只提交"事件"，不感知供应商格式。
2. **不关心返回值**：对外契约统一 `202`，业务系统永远看不到供应商投递结果。
3. **可靠送达**：**至少一次**投递，失败自动重试，不因进程崩溃或外部故障丢消息。
4. **弹性吞吐**：突发流量进缓冲慢慢消化，不被瞬间打垮。

## 二、整体架构与核心设计

```
                    ┌──────────────────────────────────────────────────────┐
                    │              Notification Service                     │
                    │                                                      │
  Business System   │  POST /api/v1/notifications                          │
    ──────────────► │  ┌────────────────────────────────────────────────┐  │
                    │  │ NotificationIngestService                       │  │
                    │  │  校验 → 幂等去重 → 落库(outbox) → 按模式分发      │  │
                    │  │  └─ SYNC ? ─► ProviderNotifier ──► 供应商 HTTP    │  │
                    │  └───────┬─────────────────────────────────────────┘  │
                    │          │ (PENDING 行)                               │
                    │  ┌───────▼──────────────┐        ┌─────────────────┐ │
                    │  │ outbox_notification   │◄───────│ Notification    │ │
                    │  │  (MySQL, 单一数据源)  │  轮询  │ Poller          │ │
                    │  │  SKIP LOCKED 认领     │        │ (退避/死信/告警) │ │
                    │  └───────────────────────┘        └───────┬─────────┘ │
                    └───────────────────────────────────────────┼───────────┘
                                                                ▼
                                                  供应商 HTTP(S) API
                                                  （headers + X-Request-Id,
                                                   {{payload.*}} body 模板）
```

### 2.1 核心设计原则

**① Outbox 表是单一数据源**
一切通知先落库，所有状态迁移都是数据库更新。进程崩溃、重启、外部故障都撼动不了它——「接单即持久化」，这是可靠性的根基。

**② 先落库、再投递**
投递发生在落库**之后**。即使"落库后、发送前"进程崩溃，记录也保持 `PENDING`，轮询器会重新拾起。**宁可重复，不可丢失。**

**③ 至少一次 + 双向幂等**
- 入站：`(provider, eventId)` 唯一约束做**幂等去重**，业务系统重复提交不会产生重复消息；
- 出站：每次请求携带 `X-Request-Id`（= notificationId），把**去重责任交给供应商**，让重试后的重复投递无害。

**④ 双模式投递，异步兜底**
按供应商配置两种模式，让"实时性"与"吞吐"分开对待：

| 模式 | 行为 | 适用 |
|---|---|---|
| `SYNC` | 先落库，再在**请求线程内立即**调用供应商；成功即 SUCCESS，失败/超时保持 PENDING 交给轮询重试 | 低量、高实时：订阅→CRM、购买→库存 |
| `ASYNC` | 仅落库即返回 202，由轮询器**批量**投递 | 高量、低实时：广告引流 |

`SYNC` 是"乐观快路径"，`ASYNC`/轮询是"兜底保障"——两者共用同一套状态机与失败计数，口径一致。

**⑤ 轮询认领 + 指数退避 + 死信**
轮询器用 `FOR UPDATE SKIP LOCKED` 短事务认领批次（认领即提交、释放行锁），逐条投递并在**各自独立事务**里更新状态，全程不持有数据库锁。失败按 `base × 2^(n-1)` 指数退避（封顶 5 分钟），达到 `maxAttempts` 后进入死信（`FAILED` 留痕），等待人工排查。

**⑥ 供应商配置驱动 + SPI**
`ProviderNotifier` 是投递适配接口，通用实现 `HttpProviderNotifier` 完全由配置驱动：URL、方法、headers（支持 `${ENV}`）、超时、投递模式、重试预算、`{{payload.*}}` 请求体模板。**新增供应商只加一段 yml，不写代码**；模板覆盖不了的场景再写自定义适配器接入 SPI。

**⑦ 失败告警**
进程内统计每个供应商的连续失败次数，跨过阈值且超过冷却期时触发邮件告警，防止"外部系统长期不可用"而无人知晓。

### 2.2 一条通知的完整旅程

```
提交 → 校验(400) → (provider,eventId) 去重
     → 落库 PENDING（maxAttempts 快照）
     → 按模式分发：
        SYNC  → 立即调供应商 → 成功 SUCCESS；失败保持 PENDING（轮询兜底）
        ASYNC → 保持 PENDING
     → 轮询器周期认领到期 PENDING
     → 失败 → attempt+1、指数退避；超 maxAttempts → FAILED 死信 + 连续失败告警
     → 成功 → SUCCESS
```

## 三、关键工程决策与取舍

| 决策点 | 取舍 | 选择 | 理由与代价 |
|---|---|---|---|
| **是否引入消息中间件** | Kafka 削峰 vs 零额外依赖 | **MVP 不引入 Kafka**，用 Outbox + 轮询 | 业务 fire-and-forget，outbox 表已能保证至少一次与削峰（异步模式）。代价：异步投递延迟受轮询间隔限制；流量上升后按 [TODO](#todo) 演进 Kafka。 |
| **实时性 vs 吞吐** | 一刀切 vs 分模式 | **双模式配置切换**（SYNC/ASYNC） | 广告要吞吐、订阅要实时，一个配置满足两种业务。购买类突发时可临时切回 ASYNC 换吞吐、牺牲延迟，无需改代码。 |
| **至少一次 vs 精确一次** | 可靠性成本 | **至少一次 + 供应商幂等** | 精确一次需要跨系统幂等与分布式事务，成本远超收益。用 `X-Request-Id` 让供应商去重，重复投递无害。 |
| **落库与投递顺序** | 先发后存 vs 先存后发 | **先落库再投递** | 先发后存一旦发送成功但落库失败即丢消息。先存后发保证不丢，代价是可能重复（已被幂等兜底）。 |
| **认领事务形态** | 长事务持锁 vs 短事务 | **SKIP LOCKED 短事务认领 + 逐行独立事务** | 投递是网络 I/O，不能持有数据库锁/连接。短事务提交即释放行锁，崩溃只丢内存中的在途处理。 |
| **重试预算** | 供应商统一 vs 按消息 | **按消息 `maxAttempts`，入站快照** | 业务方按消息重要程度自定义（请求参数优先，缺省取供应商配置）。快照保证后续改配置不影响在途消息。 |
| **失败计数存储** | DB/分布式 vs 内存 | **进程内计数（MVP）** | 最简单且够用。代价：重启重置、多实例各自计数——用冷却期抑制告警风暴，准确方案列入 [TODO](#todo)。 |
| **告警范围** | 大而全 vs 收窄 | **仅「连续失败」+ 邮件** | 先解决"外部系统长期不可用"这一个最痛场景。死信数量阈值、滞留超时、IM/Grafana 渠道列入 [TODO](#todo)，避免过度建设。 |
| **供应商接入方式** | 每供应商一段代码 vs 配置驱动 | **配置驱动模板 + SPI 预留** | 新供应商只加 yml，零代码零编译。模板覆盖不了的场景通过 `ProviderNotifier` SPI 插自定义适配器。 |
| **轮询并发模型** | 多线程抢单 vs 单线程 | **单线程轮询（pool-size 可配）+ SKIP LOCKED** | 单实例内单线程天然无并发抢单。多实例时 SKIP LOCKED 防认领竞争，但 at-least-once 下仍可能重复投递（供应商幂等兜底），边界见 [TODO](#todo)。 |

**一句话总结取舍主线**：用 **MySQL outbox + 轮询** 这一份基础设施，同时满足了「抗突发」与「不丢消息」两个诉求；把「实时性」用**双模式配置**拆开处理；把「重复」这个无法根除的问题用**双向幂等**变为无害。所有被放弃的复杂度都记为 TODO，等流量与规模证明需要时再引入。

## 四、设计说明

### 4.1 系统边界

**我选择在这个系统中解决的：**

- **屏蔽供应商差异**：业务系统只提交"事件"，不感知外部系统的 URL / Header / Body 格式差异。
- **可靠送达**：先落库再投递，保证至少一次，不因进程崩溃或外部故障丢消息。
- **失败兜底**：指数退避重试、死信留痕、连续失败邮件告警。
- **幂等**：入站 `eventId` 去重 + 出站 `X-Request-Id` 双向幂等。
- **实时性分层**：`SYNC` / `ASYNC` 双模式配置，让不同业务各取所需。
- **按消息控制重试预算**：`maxAttempts` 由业务方按消息重要性自定，入站快照。

**我明确选择不解决的（和原因）：**

- **精确一次**：跨系统保证需要分布式事务 + 供应商端幂等，成本远超收益。我选择至少一次，把去重责任用 `X-Request-Id` 交给供应商。
- **消息中间件（Kafka）**：MVP 阶段它是纯运维负担，outbox + 轮询已能满足削峰与不丢。
- **"保证实时"**：`SYNC` 只做尽力实时——供应商恰好挂了，就落到轮询节奏。
- **完整的告警体系**：死信数量阈值、滞留超时阈值、IM/Grafana 渠道，只写进 TODO。
- **重试分类、Flyway、DB 化失败计数、管理后台**：等流量与规模证明需要时再做。

### 4.2 可靠性与失败处理

我的投递语义是**至少一次**。核心不变量是**先落库、再投递**——就算进程崩溃在"落库后、发送前"，记录也保持 `PENDING` 被轮询重新拾起。代价是可能重复投递，我用双向幂等把它变为无害：`eventId` 挡业务侧重复提交，`X-Request-Id` 让供应商对重试去重。

**外部系统失败或长期不可用时，我的处理策略（按顺序）：**

1. **指数退避重试**：`base × 2^(n-1)`，封顶 5 分钟；
2. **死信**：达到该消息的 `maxAttempts` 后标 `FAILED` 并留 `last_error`，等人工排查；
3. **告警**：连续失败跨过阈值且超过冷却期时发邮件，防止"外部系统挂了一周没人知道"；
4. **数据永不丢**：外部系统长期不可用时，消息在 outbox 里躺着反复退避重试，恢复后自动续投，或最终死信由人介入。

`SYNC` 失败也走同一套状态机并退化为轮询兜底——**同步与异步两条路径的可靠性口径完全一致**。

### 4.3 取舍与演进

**我认为"过度"、没有采纳的设计：**

- **引入 Kafka**：太重。我改用 `SYNC` / `ASYNC` 双模式——实时要求高的业务用同步投递，广告引流用异步轮询，MVP 阶段完全够用，且不新增任何中间件。
- **告警的范围**：只做"连续失败 + 邮件"这一个最痛场景，其余渠道与规则列入 TODO，不为还没出现的场景过度建设。

**未来流量或复杂度显著增长时，我会这样演进：**

- **流量上来 → 引入 Kafka**：outbox 保持为数据源，新增 relay worker 发布到 Kafka topic（按 provider 分区），用 Kafka 消费 worker 替代异步轮询。`SYNC` 路径、API 契约、供应商接入层不变——演进是增量替换，不是重写。
- **多实例**：把进程内的失败计数 DB 化，解决重启重置、多实例计数不准。
- **告警完善**：补死信数量阈值、滞留超时阈值规则；补 IM Webhook（钉钉/企微/Slack）、Grafana 渠道。
- **投递策略细化**：429 之外的 4xx 视为不可重试、直接死信。
- **生产化**：`ddl-auto=update` 换 Flyway；明确多实例下轮询器"认领不重复但可能重复投递"的边界（由供应商幂等兜底）。

**现状的已知短板（不粉饰）**：`SYNC` 实时性只是尽力而为；轮询器默认单线程，吞吐有上限；进程内失败计数重启会清零；至少一次要求供应商接住 `X-Request-Id` 去重。这些在 MVP 阶段都可接受，也正是演进清单里每一条 TODO 的由来。

## API

### 提交通知

`POST /api/v1/notifications`

```json
{
  "eventId": "evt-20260827-001",      // 业务事件 ID，同一 provider 内唯一 → 幂等去重
  "provider": "crm",                  // 目标供应商名，须在 app.providers 中注册
  "eventType": "SUBSCRIBE",           // 可选，信息性
  "payload": { "customerId": "C-42", "status": "ACTIVE" },
  "maxAttempts": 5                    // 可选(1-100)，最大投递次数；缺省取供应商配置
}
```

响应：

- `202 Accepted` —— 已受理。无论内部同步/异步、投递成败，一律 202（业务系统看不到供应商结果）。响应体含 `notificationId` 与当前状态：
  ```json
  { "notificationId": 42, "status": "PENDING" }
  ```
  `status` 为信息性：`PENDING` / `SUCCESS` / `FAILED`。
- `400 Bad Request` —— 校验失败（缺 `eventId` / `provider` / `payload`、`maxAttempts` 越界、供应商未注册）。

### 出站请求

每次投递会附加配置的 headers、`X-Request-Id`（= notificationId，供供应商幂等）与按 `body-template` 渲染的 JSON 请求体。默认 `Content-Type: application/json`。

## 供应商配置（application.yml）

`app.providers.<name>.*`（前缀是 `app`，组件名 `providers` 自动拼接）：

| 字段 | 默认 | 说明 |
|---|---|---|
| `url` | 必填 | 供应商接口地址 |
| `method` | `POST` | HTTP 方法 |
| `headers` | 空 | 出站 headers，值支持 `${ENV_VAR}`（启动时解析） |
| `dispatch-mode` | `ASYNC` | `SYNC` / `ASYNC` |
| `connect-timeout` | `2s` | 连接超时 |
| `read-timeout` | `5s` | 响应超时 |
| `max-attempts` | `5` | 默认最大投递次数（可被请求参数覆盖） |
| `backoff-base-ms` | `1000` | 退避基数，指数退避封顶 5 分钟 |
| `body-template` | `{{payload}}` | 请求体模板 |
| `alert` | 关闭 | 见下 |

### body 模板语法

- `{{payload}}`：整个 payload 原样作为请求体。
- `{{payload.a.b}}`：取嵌套字段并输出 **JSON 字面量**——字符串自动带引号，数字/布尔原样，对象/数组内联，缺失键为 `null`。
- ⚠️ **字符串字段的占位符不要再包引号**：`{ "name": {{payload.name}} }`（渲染后为 `"name": "C-42"`）。写成 `"{{payload.name}}"` 会产生双重引号。
- ⚠️ **模板内禁用 `${...}`**：application.yml 里 `${...}` 会被 Spring 属性解析吞掉，占位符必须用 `{{...}}`。

### 告警配置

```yaml
alert:
  enabled: true
  consecutive-failures: 5    # 连续失败次数阈值
  cooldown-minutes: 30       # 告警冷却期，防风暴
  recipients: ["ops@example.com"]
```

MVP 仅实现**「连续失败次数」触发 + 邮件渠道**。邮件服务器通过环境变量配置（见下），未配置 SMTP 时告警静默跳过，不影响投递链路。

### 环境变量

| 变量 | 用途 |
|---|---|
| `MYSQL_PASSWORD` | 数据库密码（默认 `root`） |
| `CRM_API_TOKEN` / `AD_SYSTEM_TOKEN` | 示例供应商 token（未设置则为空串） |
| `SPRING_MAIL_HOST` / `SPRING_MAIL_PORT` / `SPRING_MAIL_USERNAME` / `SPRING_MAIL_PASSWORD` | SMTP 服务器（设置后启用邮件告警） |

## 本地运行

```bash
# 1. 建库
mysql -u root -p -e "CREATE DATABASE rc_longxinnan CHARACTER SET utf8mb4;"

# 2. 启动（默认 8080，表结构由 ddl-auto=update 自动创建）
./mvnw spring-boot:run

# 3. 用本地假供应商联调（可选）：启用 stub profile，把某供应商 url 指到 /stub/echo
./mvnw spring-boot:run -Dspring-boot.run.profiles=stub

# 提交一条同步通知
curl -X POST http://localhost:8080/api/v1/notifications \
  -H "Content-Type: application/json" \
  -d '{"eventId":"evt-1","provider":"crm","payload":{"customerId":"C-42","status":"ACTIVE"}}'
# => 202 {"notificationId":1,"status":"SUCCESS"}

# 观察投递状态
mysql -u root -p rc_longxinnan -e \
  "SELECT id,provider,event_id,status,attempt_count,next_attempt_at,last_error FROM outbox_notification;"
```
